# Persistence, ownership, and failure-handling audit

**Issue:** #130
**Reviewed source:** `8c4795f5a4ef4e55c44ff44e98ffd6413cb21c6f` (`origin/main` at review start)
**Environment:** source review and existing local/disposable-PostgreSQL evidence only
**Scope:** saved-analysis create/read/update/delete, identity-to-owner mapping, request validation, persistence constraints, retries, and failure recovery.

No hosted database or provider was contacted. No production or staging data was read or changed. This audit adds no migration or runtime behavior.

## Findings

| Area | Expected behavior | Observed implementation and evidence | Result / follow-up |
|---|---|---|---|
| Create ownership | Persist each report under a server-derived internal user ID; keep demo data separate. | `report_owner` verifies the bearer identity in Neon mode and maps `sub` to `users.id`. `persist_saved_analysis` selects the owner by that ID. Demo mode uses the fixed `demo@phishlens.test` user. `test_two_user_crud_and_legacy_separation_survive_fresh_clients` and `test_authenticated_create_retry_and_same_key_are_per_user` cover the PostgreSQL path. | Pass in source and local DB tests. Demo mode remains intentionally available as a rollout fallback; it is not Neon Auth acceptance. |
| Read and history ownership | List and detail must expose only the current owner’s records; foreign and legacy/demo records must not be claimable by matching email. | History list filters by `AnalyzedEmail.user_id`; detail joins the user and filters by owner ID. Auth tests verify each account sees only its own row and cross-user/legacy detail returns 404. | Pass in covered application path. RLS is not present, so raw database access that bypasses these routes has no row-level ownership barrier. |
| Update and delete ownership | Only the owner may edit notes/feedback or delete; foreign IDs should not disclose record existence. | PATCH and DELETE select by owner and record ID, lock the selected row, and return 404 when no owned row matches. PostgreSQL tests exercise foreign PATCH/DELETE and owner updates/deletes using fresh clients. | Pass in covered application path. No RLS defense in depth. |
| Request validation | Reject malformed, oversized, empty, or unsupported input before persistence. Limit PATCH to notes/feedback. | Pydantic schemas cap body at 30,000 characters, subject at 320, notes at 2,000, reject extra fields, reject blank bodies and empty PATCH bodies, and constrain feedback values. Create route maps request validation to a safe 422 response. | Pass by source inspection and existing unit/integration tests. |
| Persistence integrity | Enforce user/report relationship and prevent duplicate per-owner idempotency keys. | `analyzed_emails.user_id` is non-null and references `users.id` with `ON DELETE CASCADE`; migration 0003 adds unique `(user_id, idempotency_key)`. Model also constrains confidence and analysis mode. | Pass by schema/migration review and existing migration/PostgreSQL tests. |
| Idempotent retry | Same owner/key/payload returns the original record; changed payload conflicts; another owner may use the same key independently. | Create looks up a prior row scoped by owner ID (demo lookup is separately scoped by demo email). Insert uses `ON CONFLICT (user_id, idempotency_key) DO NOTHING`, then reads the winning row. Existing PostgreSQL tests cover replay, changed-payload 409, same key for two users, and an ambiguous post-commit timeout retry. | Pass in covered local PostgreSQL evidence. Do not blindly retry an ambiguous request without its original key and payload. |
| Failure rollback and recovery | Failed updates or saves must not leave partial writes; subsequent requests should continue to work. | ORM PATCH flushes and validates the response before commit; database/validation failures roll back. Create commits only after response serialization, and a closed uncommitted psycopg connection rolls back. Existing tests cover constraint/response failures, lock timeout, post-commit lost acknowledgement, and later healthy persistence. | Pass in covered local PostgreSQL evidence. The psycopg create path is a separate connection from the SQLAlchemy history/PATCH/DELETE path and must be included in any future RLS transaction-context work. |
| Authentication claims and revocation | Require a valid, verified, active Neon Auth identity before resolving an owner, and define how already-issued tokens behave after account suspension or session revocation. | JWT validation requires signature, issuer, audience, expiry, issued-at, subject, and verified email. The implementation rejects `banned: true`, but accepts a token with no `banned` claim. It does not check the current Auth account/session state or a revocation list; a token that passes validation can therefore remain usable until expiry if its account is later suspended or its session is revoked. | **Open contract/security gap:** confirm Neon’s actual token claims and revocation behavior. Decide whether signed claims are sufficient for the token lifetime or whether an additional current-status/revocation check is required. Tests currently cover a token with `banned: true`, but not an absent `banned` claim or post-issuance suspension/revocation. No hosted Auth acceptance was performed. |
| Schema compatibility | Existing saved rows should remain readable as migrations evolve. | Migration 0004 adds nullable unique `users.neon_auth_subject`; existing rows remain unmapped and are not claimed by email. Prior disposable-PostgreSQL migration lineage and saved CRUD evidence are recorded in PR #219’s migration-recovery work. | Pass for local migration/schema evidence at the referenced source; not a live-database guarantee. |
| Sensitive saved content | State accurately how saved email bodies are protected. | Saved email body and subject are stored as ordinary text columns. Database/platform encryption is not application-level field encryption. | Deferred security work: agree on threat model, key custody, access/deletion requirements, and migration strategy before implementing field encryption. |

## Evidence basis

The reviewed source contains these relevant tests:

- `backend/tests/test_report_auth_postgres.py`: two-user CRUD and legacy separation, per-user idempotency, missing/expired/unverified token rejection, email-collision non-claiming, concurrent subject mapping, and stable mapping when email changes.
- `backend/tests/test_saved_create_postgres.py`: saved create/retry, changed-payload conflict, post-commit acknowledgement loss, constraint/response rollback, recovery after failure, and lock-timeout behavior.
- `backend/tests/test_saved_crud_postgres.py` and `backend/tests/test_history_postgres.py`: owner read/update/delete, isolation, empty history, and rollback behavior.
- `backend/tests/test_analysis_persistence.py`: insert and conflict behavior for the psycopg persistence helpers.

Previously reported disposable-PostgreSQL run on the reviewed source revision: backend suite **354 passed, 2 skipped**. The exact environment, command, migration/seed checks, and scope limits are recorded in [PR #219’s migration compatibility evidence](https://github.com/kendshhh/PhishLens/blob/d373110dede30d74c4e1ec1ff977976125e90f7b/docs/migration-compatibility-recovery-2026-11-15.md). That is local evidence, not CI, hosted staging, production, or real-Neon-Auth evidence. The skipped tests were not counted as passing PostgreSQL coverage.

## Conclusion

The reviewed code has application-level per-user ownership enforcement, bounded input schemas, database integrity constraints, scoped idempotency, and rollback/retry coverage in local PostgreSQL tests. This does not establish RLS, application-level encryption, or hosted Neon Auth acceptance. The active-account claim and session-revocation contract remains open: the implementation does not check current session state, and its `banned` rejection only applies when that claim is present and true. No runtime fix is proposed by this audit until the contract is confirmed.
